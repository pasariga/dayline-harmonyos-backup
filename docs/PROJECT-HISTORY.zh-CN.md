# Dayline（内部项目代号：DDL）

Dayline 是一款面向大学生的 Deadline 进度与风险管理 App。它不只记录截止日期，还会结合任务拆解、完成进度、剩余工作量和截止时间，帮助用户判断风险、确定今天最该做什么，并自动生成和动态调整倒排计划。

本文档既是项目说明，也是交接给 ChatGPT、Codex 或其他 AI 的工作上下文。任何 AI 在修改本项目之前都应先阅读本文档和实际代码；每次完成任务后，必须同步更新本文档中的项目状态、改动记录和验证结果。

## 产品核心流程

```text
打开“今天”
  -> 看到首要行动，开始这一步
  -> 进入 Deadline 的“行动”工作面
  -> 完成任务或更新手动进度
  -> 原业务服务重算风险、共享容量、今日行动与排期
  -> 情况变化时，在“工作量与计划”偶尔校准剩余时间

新 Deadline：名称 + 截止日期即可保存
  -> 工时、任务、进度模式、提醒按需要补充
```

V1.0 正式开放的主要能力：

- Deadline 新建、查看、编辑、删除、完成与恢复，以及逾期处理；
- `relationalStore` 本地持久化，以及旧版 Preferences 数据的一次性迁移；
- 手动进度和自动进度两种模式；
- 多层级任务的添加、编辑、删除、完成与自动进度计算；
- 初始预计总工作量、主动确认的当前剩余工作量、风险分析和可解释的优先级；
- “今日行动”推荐；
- 多 Deadline 共用每日容量、自动倒排计划和基于最新状态的动态重排；
- 统一设置页，以及跟随系统、浅色、深色三种主题模式；
- 跟随系统或手动选择 App 语言；
- 简体中文、繁體中文、English、日本語、한국어、Deutsch、Español、Français 本地化资源。

## 数据模型与持久化

主数据库为 `ddl.db`，当前数据库版本为 8（仅增本地旧云暂存表，未解除云同步发布阻塞）。主要表包括：

- `deadlines`：保存 ID、名称、类型、截止日期和时间、备注、创建时间、完成状态、初始预计总工作量、当前剩余工作量及确认状态/时间、进度、进度模式、提醒设置等；
- `deadline_subtasks`：保存 Deadline 下的层级任务、父任务关系、顺序和完成状态；
- `deadline_reminder_states`：保存已调度提醒的标识、时间和签名，用于更新或取消旧提醒；仅本机。
- `ddl_sync_events`：不可变完整聚合事件及永久删除信息；当前实际云交换门禁关闭，验收通过后才交换此表。
- `ddl_sync_archive`、`ddl_sync_issues`、`ddl_sync_owner`：本机已见历史、冲突/缺项状态、数据库唯一关联账号；不参与云同步。
- `ddl_legacy_imports`：V8新增本地冻结旧数据暂存、导入回执及问题，不参与云同步。

V6→V7保留原业务字段并建立幂等历史；V7→V8只新增暂存表。任务/进度/事件同事务，按因果合并，同字段冲突明确选择，永久墓碑防复活。云最低协议2，原可信协议1历史字节不改写，以一次新版封装传输；新收到的未核验协议1修改隔离。旧云本地分页协调和导入处理器已实现；完整历史及暂存批次先一起保存，历史先投影，再处理旧基线。本轮增加原生隔离接收候选及Shadow分析，但真实网络门禁继续关闭：云注册隔离、实际schema/来源账号、冻结/完整删除证明和服务端旧写拒绝未验证。不能把新事件表为空理解成无数据或无删除。完整规则与真实云发布阻塞见 [同步可靠性报告](../SYNC_RELIABILITY_REPORT.md)第9–13节。

核心模型位于 `entry/src/main/ets/models/Deadline.ets`：

- `Deadline`
- `DeadlineSubtask`
- `DeadlineReminderState`

数据修改必须继续通过现有 service 层完成，不要在页面中另建一套数据库访问逻辑。不得破坏已存在用户数据或擅自改变表结构；如确需升级数据库，必须提供兼容迁移方案。
