## 产品语义

| 内容 | 当前行为 |
| --- | --- |
| 截止日期、时间输入 | 保存时按设备所在地的日历和钟面解释，形成固定截止时刻 |
| `deadline_at` | 权威的 UTC epoch 毫秒；旅行不会移动截止时刻，只改变当地显示 |
| `deadline_date/time` | 原录入文字，兼容保留，不包含来源时区；不用于覆盖已知绝对时刻 |
| 普通字段编辑 | 截止选择未改变时保留原截止三元组，不重新解释；明确修改日期/时间才使用当前时区 |
| 创建、确认、提醒登记、同步历史时间 | 绝对时刻；同步事件仍不按墙上时钟判因果先后 |
| 今天、剩余天数、日计划、每日摘要 | 当前时区的自然日期；23/25 小时日仍各算一天 |
| 摘要钟点、免打扰 | 当地重复钟面时间，跨午夜用日历推进 |
| 提前 1 小时 | 真实 60 分钟持续时间 |
| 提前 1/3 天 | 当地前 1/3 个日历日同钟点；不是减固定 24/72 小时 |
| 剩余估计有效期 | 沿用既有 336 小时持续时间规则，不改为 14 次午夜；14 个自然日跨 DST 可是 335/337 小时 |
| 系统时钟早于确认时间 | 估计保留，但暂标过期并降级小时风险/排期；时钟恢复后重新判断 |

缺少来源时区的历史文字无法恢复当时地区；不猜测、不回填数据库。已有 `deadline_at` 的记录按固定时刻处理。只有文字而无可靠时刻的旧云兼容链路保持冻结，本轮没有迁移真实历史云记录。

新建选择过去或当前时刻时，保留输入并提示改选未来时间；历史编辑允许过去。新选择若处于春季不存在的时间或秋季重复时间，则要求改选明确时间。已有重复时刻的记录在未改截止的编辑中保留原值。

日历运算由本地日期构造器推进。`Date.UTC(当地年/月/日) / 86400000` 仅给日期标签编号，不是测量当地一天的长度；风险冷却、逾期小时和估计有效期仍使用持续时间，属于正确的固定时长用途。既有每日日容量保持原预算，部分日按实际区间比例计算。

## 实际发现与修复

| 位置 | 原因 / 触发 | 修复后的行为 |
| --- | --- | --- |
| DeadlineScheduleService | 本地午夜差除 24 小时再取整，春季少算一个日期 | 用日历日期序数算天数，逐自然日分配统一容量 |
| TodayActionService、Index | 持续时间进位天数与当天边界混用 | 当天、剩余天数按当地日历；同日优先关系仍按绝对时刻 |
| AppSettingsService | 超长区间回退路径将完整自然日当固定 24 小时 | 完整日期计数，部分日用实际长度；不改每日预算规则 |
| CreateDeadline | 编辑时用旧录入文字重建当地时刻，换时区可能移动截止 | 无截止修改则原三元组逐值保留；改截止才按当前时区计算 |
| DeadlineDetail / Index | 次要信息继续显示旧录入字符串 | 从同一个绝对截止时刻本地化显示 |
| LocalizationService | Phone 纽约时区下隐式 Intl 时区与 Date 不一致 | 显式传系统时区，遵循系统 12/24 小时；钟面草稿独立格式化 |
| DeadlineReminderService / NotificationPolicy | 1/3 天提醒减固定小时，DST 后钟点漂移 | 自然日偏移；摘要、免打扰使用当地日历，重复时段结束不回到过去 |
| EntryAbility / 三个核心页面 | 系统时钟事件原来只协调通知 | 复用 TIME/DATE/TIMEZONE 事件通知可见页，前台恢复重算，保留输入草稿 |
| DeadlineInsightService | 时钟回拨到确认之前仍把负年龄当新鲜 | 保留数值与确认时刻，暂降级；不使用负年龄做可靠估计 |

纽约原生诊断使用固定公共时刻，观察到 `Date=23:59`、隐式 Intl `21:59`、显式纽约 Intl `23:59`。原 UI 也显示 21:59，修复后显示 23:59，证据为 `ny-created.*` / `ny-format-fixed.*` 和原生格式测试。普通编辑换时区后的 UTC 不移动由应用保存后只读数据库核对。

可见页面的刷新仍为至多每分钟一次，并在最近截止点或下一午夜提前唤醒；隐藏页停表，恢复及系统时钟事件立即重算。没有 TIME_TICK、高频轮询、复杂后台机制，也没有修改系统日期/时间来做验收。

### Calendar API 重复小时限制

当前 Calendar 发布参数只表达当地年月日时分，无法编码秋季重复小时的第二次出现。发布前检查是否能够精确往返；不能表达时走现有“提醒未登记”失败反馈，不把第二次时刻偷偷提前到第一次。业务保存不因此撤销，已保存截止时刻也不改变。

这是一项诚实的安全拒绝，不是该边缘场景送达通过。需要可用真机进一步验证 Calendar/Timer 能力及重叠小时的正确送达方式；本轮不引入替代后台服务。春季日历偏移落入缺失钟点时遵循原生 Date 前移规则，创建截止输入则严格拒绝隐式前移。[ECMAScript Date 的本地时间转换定义](https://tc39.es/ecma262/2025/multipage/numbers-and-dates.html)为基础行为依据，Phone 测试用于核实当前运行时。
